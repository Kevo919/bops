## What was checked

- #69 leaks: the 503 body is `{unreachable: true, error: e.message}`. That is the same `e.message` the old 500 already sent, so nothing new leaks. The Honcho SDK's messages are the service's response `message` or fetch's TypeError text. Neither carries the API key. The UI now renders a fixed sentence instead of `data.error`, so the window and the phone (which use the same components; nothing else reads GET /api/memory) show less than before. A probe with `HONCHO_API_KEY=hc-SECRETKEY-123` and fetch offline returned `{"unreachable":true,"error":"offline: api.honcho.dev"}`, with no key in it.
- #69 owner/member rules: only the catch block of GET changed. No gating changed in the route or in proxy.ts. POST is untouched.
- #69 memory off: the 503 sits behind `memoryOn()`. With memory off, the failure is the old 500 `{error}` with no `unreachable` field (tested).
- #69 every reader of GET /api/memory: there are three, at bot-memory.tsx:56 (the page), bot-memory.tsx:71 (search) and memory-sheet.tsx:43 (the sheet). The page and the sheet handle it. Search does not (D2).
- #72: the message holds no key value. The path is a placeholder (`C:\Users\<you>\bops\.env.local`), and the TS `\\` escapes come out as single backslashes. The only behaviour change is the message text. The test confirms zero fetches without a key and one fetch with a key. A grep found no code that writes `process.env.OPENAI_API_KEY`, which supports the claim that "a key saved in Logins doesn't power the chat".

## Defects (none block)

- **D1 (medium) lib/server/memory.ts:872 vs components/app/memory-sheet.tsx:81.** `memoryInfo` swallows card failures (`card(b).catch(() => [])` inside `within(...)`). When Honcho is down, `GET /api/memory?ws=…` returns **200** `{on:true, card:[]}` and the sheet shows a normal, empty memory, not "Can't reach". A probe confirmed it: `?ws=main` and no-ws both gave 200 with fetch offline, while `?bot=` gave 503. The sheet's new branch only fires for throws outside the Honcho call. scripts/test-memory-reachable.mjs covers only `?bot=` and checks the sheet by regex, so this gap goes unseen.
- **D2 (low) components/app/bot-memory.tsx:73 (rendered at :176-181).** The search effect does `setResults(j.facts ?? [])`. When the service is unreachable, a search shows "Nothing learned matches. Press Ask…", which is the wrong reason again, on the search path.
- **D3 (low) app/api/memory/route.ts:20.** Any throw while memory is on is labelled `unreachable`, and the tab says "It's set up, but it didn't answer". That includes a 401 from a wrong `HONCHO_API_KEY`, `bankFor`'s "Memory isn't available right now." (no cloud prefix) and plain code bugs in `memoryFor`. A bad key gets told "try again in a moment". Telling auth errors (HonchoError status 401/403) apart from connection or timeout errors would fix it.
- **D4 (info) app/api/memory/route.ts:20.** The raw `e.message` is still forwarded in the 503 body (no regression, no secret seen). The UI no longer needs it. Dropping it, or logging it on the server only, would close the door on a future upstream message that carries a URL.
- **D5 (nit) lib/server/openai-client.ts:41.** "the .env.local file next to the app" fits a linked Windows build only loosely. That build runs in the checkout recorded in desktop/repo.json (desktop/main.cjs:437 `cwd: REPO`; docs/windows.md), not next to the installed app under the user's account. "in the Bops folder the app was built from (like C:\Users\<you>\bops\.env.local)" would be exact. The example path itself is fine.
