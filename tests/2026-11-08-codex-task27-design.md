# Task27 design proposal — signed routine events
2026-11-08T03:18Z | Codex | Architecture | Review Needed
No application code changed. Approval from lead required before implementation.

## Scope and existing pieces
Add Schedule {kind:"event", source:"webhook"|"mail"} per task27, mutually exclusive with timed cadence for first release. Existing timed/calendar schedules remain unchanged; event schedules never enter time-based due calculation. Reuse app/api/routines/route.ts owner window management, lib/server/routines.ts run()/chatRun()/taskRun(), history, delivery and session lifecycle. New trigger admission wrapper must check routine.enabled itself: runRoutine currently does not. Never pass manual:"app" for outside events: that marks owner present and bypasses the away brake.

Proposed files: lib/types.ts, cloud/schedule.ts event exclusion, lib/server/routine-events.ts (new admission/signature/ledger), lib/server/routines.ts (event run context), app/api/routines/[id]/hook/route.ts (new POST), separate owner-management trigger route, proxy.ts exact hook-path predicate, lib/server/mail.ts, cadence-picker/routines editor and feature-status registry. Tests in a dedicated suite plus proxy/routine/mail integration and fork CI. Approval enforcement changes will be scoped after tracing every outward action path; not a prompt-only implementation.

## Webhook protocol and admission
POST /api/routines/{id}/hook, application/json only; no query credentials. Headers X-Bops-Timestamp (canonical decimal Unix seconds), X-Bops-Delivery-Id (bounded random ID), X-Bops-Signature (v1=64 lowercase hex). HMAC-SHA256 over version + newline + routineID + newline + timestamp + newline + deliveryID + newline + exact raw body bytes. Reject ambiguous headers/invalid encoding and unknown versions. Strict +/-300 second freshness. Decode fixed-size hex and compare with timingSafeEqual only after length/format validation. Do not parse/re-serialize before verifying.

Stream body with hard64KiB cap even without Content-Length; reject compressed bodies, oversized declared or streamed bodies, malformed JSON and unsupported content types. Bound header/ID sizes. Generic auth failure must not enumerate routine IDs. No request body, secret or signature in logs; outcome labels and random delivery reference only.

Require active owner account/workspace, enabled routine and enabled source, valid secret generation and inactivity brake before enqueue. Caller cannot choose bot, goal, model, destination, computer or permissions. Rotation/disable invalidates queued but unstarted deliveries; recheck identity/state before execution. All routine types get one active event-run limit, not just taskRun's existing task-session check.

Replay/rate: durable account+workspace+routine+generation+deliveryID ledger, atomic claim before execution; concurrent duplicates return same generic accepted receipt without rerun. Retain IDs15min (covers full timestamp window plus skew); bounded entries and capacity fail closed rather than evicting still-valid entries. Proposed limits: per-routine10 accepted/minute, account60/minute and bounded global preauth ingress; return429 on saturation. No IP trust from caller-supplied forwarded headers. Persist pending/claimed/terminal state; crash recovery marks ambiguous started events interrupted, never blindly replays them. At-most-once admission, not a promise of exactly-once external effects. Implement one authoritative writer per local install; multi-worker/cloud deployment stays unavailable until a transactional unique constraint backend exists. Do not rely on an in-memory Set for restart safety.

## Secrets and management
32 random bytes; server-only account-scoped store under userDir, using phone.ts phone-secrets.json isolation precedent. This existing precedent is local file storage, NOT encryption or a drop-in external keys.ts broker vault. Owner-only restricted permissions/Windows ACL must be enforced before writing; fail closed if unavailable. Secret values never join Routine/state sync, snapshots, API lists, logs or URLs. Reveal new secret exactly once in successful owner-only no-store response; later GET returns enabled/generation/last-result metadata only. Create/rotate/disable require existing fromBopsWindow + readiness + owner/account checks; no paired-phone, member or bot-management access. Rotate fresh random secret, revoke old generation immediately and invalidate outstanding deliveries. Delete clears secret and ledger. Lead decision: accept this existing local-secret storage class, or require OS-backed encryption before shipping; do not claim encrypted storage absent implementation.

## What the bot sees and outward actions
Routine definition remains the trusted instruction. Event payload is size-capped quoted data with explicit source metadata and untrusted markers; omit attachments in v1. Limit model-visible text8KiB and disclose truncation. JSON fields cannot override run options. Quoting alone does not prevent prompt injection: carry a non-model-controlled externalEvent execution context through routine/chat/task dispatch. All outward actions from that context must require a fresh owner approval regardless of auto-reply, trusted routine, prior thread grants or sender status. Test real permission branches, not only prompt wording. If an execution path cannot enforce this context end-to-end, block that event routine type in v1 rather than claiming safety. No event may alter schedules, secrets or permissions.

## Reachability — no automatic public exposure
Choose private/local transport for v1, not Funnel or a public relay. A local sender on the PC posts to loopback. A sender on the existing VPS/tailnet (for example n8n) posts through the already configured tailnet HTTPS serving path, with HMAC still mandatory. PC external delivery remains unavailable unless an owner explicitly configures a narrow tailnet listener; we do not change bind address, firewall, Tailscale Serve, n8n or Traefik automatically. proxy.ts admits only POST matching the exact hook path to its own signature verifier, never all routines endpoints; management retains window-only rules. No new cloud-tunnel REPLAYABLE entry or upstream edge relay access.

Internet-only SaaS cannot directly reach localhost/tailnet: UI must state this and not offer a misleading public URL. A future separately reviewed relay could forward just signed bounded hook POSTs; no Funnel of the full Bops app. This is a deliberate first-release limitation requiring lead agreement, not silent public exposure.

## Email arrival policy
Reuse AgentMail receive()/catchUp() after existing inbox/account checks and message-ID dedupe; no public email route. Default eligible sender only the owner's address with existing isFromOwner/DMARC-authenticated identity, correct routine bot inbox and current workspace. Reject spoofed From, bulk/auto-generated/bot mail. Other senders are unsupported until an explicit allowlist+authentication policy is approved. Dedupe by inbox/messageID with durable ledger per routine; account-switch checks repeat after awaits. Only new mail received after trigger enable time; reconnect catch-up may admit unseen mail within a bounded15min freshness window, never historical inbox floods. Mail that launches an event must not also trigger an automatic reply bypassing the event approval policy; keep inbox card, route through one approved handling path.

## UI and acceptance
Cadence choices: When a webhook arrives / When an email arrives. Show source, private reachability limitation, enabled/disabled, endpoint, reveal-once/copy secret, rotate/revoke, last outcome, and owner-only setup. Email shows owner-only sender policy. Registry badge remains in progress until deployed live acceptance; percentages are lead-owned. Do not label ready simply because secret exists.

Tests: valid signed admission; every modified signed component; missing/bad signature; +/-window edges; malformed timestamp; duplicate concurrent/restarted delivery; crash ambiguity; expired ledger retention; rotation/disable/delete; disabled routine and away brake; cross-account/routine access; account switch during awaits; streaming oversize/Content-Length lies; flood/capacity/queue limits; owner/member/phone/bot management gates; no secret in state/logs; actual outward approval enforcement including preexisting grants; mail spoof/DMARC/bulk/catch-up/double-handler; event excluded from timer scheduler; existing cron regression. Required tsc/lint and CI. Live: one private signed delivery starts exactly one harmless Windows task, repeated delivery does not; mail owner trigger similarly. Live/window/build hold respected.
