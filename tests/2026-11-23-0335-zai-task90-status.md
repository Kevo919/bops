## A product bug on the Windows port (found and fixed, commit 921b35c, not reviewed)

`app/api/skills/route.ts`, the `import` action, took only paths starting with `/`. Every folder on Windows starts with a drive letter, so **importing a skill or app from a folder was refused on Windows** with "Pick a folder.". The audit had this down as a failing suite; it is a failing app.

One-line fix: `path.isAbsolute(path)` in place of `path.startsWith("/")`. On macOS and Linux `isAbsolute` accepts exactly what the old check did. On Windows it also accepts a drive letter or a network share. A path that is not a folder is still refused further on, where the folder is opened.

Verified on the Windows PC: `npx tsc --noEmit -p .` exit 0 with no output; `npm run lint` exit 0, 0 errors, 35 warnings, none on a line this adds (one is in `test-chat-compact-ui.mjs`, on an upstream line of 30 Oct). With the fix, `test-skills`'s import check is no longer refused for a path under the scratch folder.

Not verified: not run on macOS or Linux; the import is not finished by that check on Windows yet (it next differs on a link that points inside the folder); not tried in the app itself. **This is a change to the app and needs the lead's review.**

## Later the same day (04:30 UTC): test-skills traced to one root cause, 25 of 27

With yesterday's route fix in place and six test-side changes (the 5-line recipe, plus the import check's
expectation for the chmod-ed script: on Windows the import truthfully records `executable: false`, so the
expected tuple says so for win32 only), test-skills runs 25 passed, 2 failed. Not committed: not green.

The two that remain are one thing, and it is a question for the lead, not a test fix:

`isScript` (lib/server/skill-bundle.ts) marks a file as needing approval when it is executable, under
`scripts/`, or starts with `#!`. A program that is none of those - an ELF binary in `bin/`, say - is caught
only by the executable bit. **Windows has no such bit, so on the Windows port such a program is not flagged
for approval at all.** The two failing checks (`Programs: a binary file is kept byte for byte`, `Apps with
programs and Orgo`) both assert the POSIX behavior, and several assertions inside them depend on the flag.

Making the test expect the Windows behavior would accept that difference silently. It looks security-
relevant (the approval gate exists before a bot runs a program), so it needs a ruling: should `isScript`
treat extensionless files under `bin/` (or known binary magic) as programs on win32, or is the difference
accepted? Until then test-skills stays at 25 of 27 and off the branch.

Also fixed today on the way (same Windows exec-bit class, each test-side): the import check's expected
`executable` for the chmod-ed script, and one more stale `Apps and source control \(5\)` in regex form.
The publish error "That app was deleted." was only a cascade of the unfinished import; it is gone.
