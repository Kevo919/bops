## #45 several accounts per provider: one defect (medium)

Checked and fine:
- Labels must match `^[A-Z0-9_]{1,24}$` in llms.cjs, lib/accounts.ts and setLlms.
- The key name is always `ROUTE_KEYS[provider] + "__" + LABEL` (`provider-accounts.ts accountKey`). No request can name another variable: an account can't reach ORGO_API_KEY or another provider's base.
- Responses, state (`chatKeys` `provider__LABEL: true`) and key-check rows carry labels and set/not-set only.
- `refusal()` redacts the key it actually sent. key-check `probeOf` only builds account probes from real probes plus a valid label, sends to the fixed URL, and excludes the executor, Orgo and Ollama.

Defect:
1. **OpenAI accounts are accepted but never used (medium, wrong key and billing).**
   - Where: `lib/server/chat-providers.ts:453-458` `respond()` sends any `openai/...` model to `client.responses.create` on the default openaiClient. Account lookup happens only in `createOnProvider` (`:358`), which refuses openai.
   - What breaks: an LLM `provider: openai, account: SIDE` chats on OPENAI_API_KEY (or the Orgo proxy). The UI still offers the choice: the Models card, key-check rows "OpenAI (side)" and `chatKeySet` on `openai__SIDE`.
   - Fix: either pass the account's key into an OpenAI client for that call, or refuse `account` for openai in llms.cjs/the card.

## #51 goals and ideas: FAIL (one high, two medium, low ones)

Checked and fine:
- set_goal and save_idea are offered only on the owner's own turns: not outside, not a member, not a background run (chat.ts:2067). They are also in NOT_FROM_MEMBER, NOT_FROM_OUTSIDE and NOT_IN_BACKGROUND.
- `/api/goals` has the standard owner-only gate.
- Routines from a goal go through `createRoutine`, so the 15-minute minimum (normalizeSchedule clampEvery) applies.
- Ideas are capped at 200 and 90 days.

Defects:
1. **set_goal's schema breaks OpenAI strict function calling (high, every owner chat turn on the OpenAI path).**
   - Where: `lib/server/chat.ts:2076-2084`. `fn()` sets `strict: true` (`:203`), but the `steps.items` object has no `additionalProperties: false`, and `title` isn't in its `required`.
   - Why it matters: OpenAI's strict mode refuses the whole request when any nested object breaks either rule. set_goal is in the tool list on every owner turn, so those turns would get HTTP 400.
   - Not seen live: there is no key here, and the tests fake OpenAI. test-chat-tools only checks top-level `required` for some tools.
   - Fix: add `additionalProperties: false` to the items object, and make `title` required (it can be null).
   - Same pattern, outside this review: `make_doc` from #41 (`:2125`, the `sections.items` and `table` objects).
2. **set_goal hands the model's raw schedule to createRoutine without `toSchedule()` (medium).**
   - Where: `chat.ts:2728` passes `o.schedule as Schedule` raw. The schedule tool converts first (`scheduleFor` → `toSchedule`, `chat.ts:154`). `normalizeSchedule` reads the stored shape, not the tool's.
   - Monthly steps: the model sends `day_of_month`, the code expects `dayOfMonth`, so the routine is refused.
   - `every` / `before_event` with `from`/`to`: normalize reads `hours`, so the window is dropped. "Every 30 min, 8-20 on weekdays" runs around the clock.
   - Fix: run each step through `toSchedule()`, as schedule does.
3. **Failed steps are silently dropped and the bot is told "Done" (medium).**
   - Where: `lib/server/goals.ts:26-28` ignores `r.error`, and `chat.ts:2733` still answers "Done … set with its routines".
   - Combined with #2, the owner is told a goal is set while some or all of its routines don't exist.
   - `/api/goals` idea-to-goal has the same gap, and also makes an orphan goal for a botId that doesn't exist.
4. **set_goal skips the "address not seen" check that schedule applies (low/medium).**
   - Where: scheduleFor runs `ctx.unseen(a.goal)` (`chat.ts:1395`); set_goal does not run it on any step's `what`.
5. **`state.goals` has no cap and settled goals are never pruned (low).**
   - Where: `goals.ts:30`.
   - Each set_goal adds up to 12 routines, and there is no overall routine cap. This is owner-only and slow-growing.

## #32 a bot's own MCP servers: earlier findings A, C, E, F fixed; B and D partly; two new gaps

- **A: fixed, with a nit.**
  - Fixed: stdout is buffered to whole lines (`mcp.ts:191`), and test-mcp passes >64KB pages.
  - Nit (low): `d.toString()` decodes each chunk separately, so a multibyte UTF-8 character split across chunks is garbled. Use `setEncoding("utf8")` or a StringDecoder.
  - Nit (low): `r.buf` has no cap, so a server that never sends a newline grows memory without limit.
- **B: mostly fixed.**
  - Fixed: PATH+PATHEXT resolution (`resolveOnPath`); .exe is spawned directly and only .cmd/.bat go through the shell; the Windows env includes SYSTEMROOT, USERPROFILE, APPDATA, LOCALAPPDATA and PATHEXT.
  - Still open (low): the cmd line quoting (`mcp.ts:163`) quotes only on space or `"`. It strips embedded quotes (a JSON arg is mangled), and leaves `& | < > ^ %` bare (a URL arg with `&` splits the line). This is the owner's config, so not a security issue.
  - Untested: the Windows test fixture names `fake-mcp.cmd` with its extension, so bare-command resolution isn't covered.
- **C: fixed.** call_mcp is in NOT_FROM_MEMBER (`chat.ts:1277`), and mcpNote is left out on outside turns.
- **D: partly fixed.**
  - Fixed: a failed initialize stops and kills the child; `running` is on globalThis; children are killed on exit.
  - Defect (medium, Windows): every kill is `proc.kill()` (`mcp.ts:110, 246, 256`). For a .cmd server (the usual `npx` case) that kills `cmd.exe` only, and the node server under it keeps running: on idle stop, on error, and at exit. The repo already uses `taskkill /PID <pid> /T /F` for this (`lib/server/local.ts:380`, `local-codex-chat.ts:115`).
  - Low: a start race. A second caller gets the `running` entry before the handshake finishes and can send `tools/list` before `initialize` has answered.
  - Low: `withServer` kills the server on any error, including a tool's own JSON-RPC error.
- **E: fixed for call_mcp.** Every call asks unless `allows(..., { justDoIt: false })` has a saved rule. readOnlyHint is collected but unused. Descriptions are capped to 300 characters and their first line, and labelled as outside text.
- **F: fixed.** The approved resume passes `approved`, and the Always allow rule matches the action `Use <server>.<tool> (MCP)`.
- **New defect (medium): the brain-thread path skips C and E.**
  - Where: `sessions.ts:2281` `...brainMcp(botId)` gives the bot's key-less servers to every brain thread of that bot. That includes member- and outside-started threads.
  - What breaks: the bot's MCP servers run with no per-call owner approval, which is the guarantee E gives the chat.
- **New defect (low): server names aren't reserved.**
  - Where: brainMcp is spread after `screen` and `browser`.
  - What breaks: a config server named `screen` or `browser` replaces Bops' own (the `screen` one carries the `--approve` flag).
  - Also low: a Windows-style command (`C:\...`, `.cmd`) is passed unchanged to the Linux computer.
