# Test: end-to-end UI crawl of every screen (web UI, self-hosted, throwaway data)

- Kind: Live server (automated browser crawl, in a Linux container, NOT on Kevin's PC)
- By: Claude (subagent for the lead), 2026-11-05 05:15 to 08:07 UTC
- Code: `windows-port` at 1829f4d (Merge #63), `npx next build`, `next start -p 3210`
- How it ran:
  - Server self-hosted (`BOPS_SELF_HOSTED=1`), scratch HOME, its own `.data`, random `BOPS_UI_TOKEN`; the browser got the `bops_window` cookie as `desktop/main.cjs` sets it. A fake Orgo on 127.0.0.1 answered sign-in (device flow), profile and the key vault, so the app signed in as a made-up user and Issues, Tasks, People and Knowledge showed.
  - Seeded state: 2 workspaces (Main, Side Project), 4 bots (Boppy, Rook, Pip; Kai in Side Project), 4 bot chats + a group chat with messages, a done and a failed thread, 3 routines (weekdays, weekly paused, a once reminder), a goal, an idea, and an email approval card. A fake `OPENAI_API_KEY` sits in the fake vault ("key set"); every other provider shows "no key".
  - No real keys anywhere. Network: the browser's requests off 127.0.0.1 were aborted and logged; the server ran with a preload that refuses every socket off loopback and logs it. Nothing reached a real provider.
  - The window was told it runs on Windows (`/api/config` platform `win32`) so it shows the words a Windows user sees.
  - Per screen: screenshot (deviceScaleFactor 1), console errors, failed `/api` calls (>= 400), uncaught exceptions, Next's "Application error" page, buttons with no effect, layout checks, and "Mac" words. Every control in the screen was clicked (or filled with valid, empty, 3000 char and wrong format input); destructive ones were clicked and then cancelled at their confirm; external links were recorded, not opened; Restart Bops, Sign out, Call and the microphone were skipped. The data was reset after anything that changed it.
  - Sizes: 1280x800 (all clicks), 420x800 (every screen entered), phone 412x915 with the paired phone's `bops_remote` cookie and no window cookie (every screen entered; 6 screens clicked through).
  - Scripted extras: cron picker with good and bad expressions, new bot with empty, blank, 200 char and good names, group chat, model picker, sending a message with no real key, the approval card, SOUL.md and MEMORY.md with 16, 0 and 20,050 chars.

## Result

**44 screens reached at 1280x800, 969 controls clicked or filled. 0 uncaught exceptions, 0 "Application error" pages, 0 React crashes.** 4 nav places don't exist in this build (AI plans: brains off; Privacy: self-hosted; Your Apps and Domains: not an @orgo.ai account), so they were not crawled.

Pass/fail: **⚠️ the app holds up at desktop size; it is not usable at 420 px or on a phone (412 px)**, and 3 small bugs were fixed (PRs below).

## 2. Bugs

### High

**H1. The UI has no narrow layout: at 420 px and on a phone (412 px) the sidebar takes 340 px and every page is cut off.** Severity High for the phone (the Android app is a WebView of this same page: `android/.../MainActivity.kt` loads `$address/`, no `useWideViewPort`; `app/layout.tsx` sets no viewport). At 420x800 15 screens could not be reached at all (chat More menu, routine editor, Skills, New tab, the bot panel, every bot page), on the phone the same 15 plus 70 % of the clicks in the 6 screens tried failed as "covered or off screen". The chat column is about 80 px wide; Settings shows only "Settin…" and a cut nav; its content is past the right edge. The layout checker found no "overflow" because it is all clipped inside the app's columns, so it looks tidy and is unusable.
- Repro: open the app in a 420 px wide window (or the Android app), open any chat or Settings.
- Screenshots: `tests/e2e-2026-11-05/narrow-420.png`, `tests/e2e-2026-11-05/phone-412.png`.
- Electron itself can't get this narrow (`desktop/main.cjs` minWidth 1180), so this hits the phone, a browser side panel and a hosted server, not the Windows app window.
- Likely files: `components/app/bops-app.tsx` (the column layout, `sidebarOpen`), `components/app/sidebar.tsx`, Settings' fixed 240 px nav (`Settings` in bops-app.tsx). Too big for a small fix: needs a one-column mode under ~700 px (sidebar as its own screen, Settings nav as a list that opens its pane). For the lead.

### Medium

**M1. Unpair and Pair again lock the phone out on the first click, no confirm.** Every other destructive button the crawl hit asks first (Remove key, Delete routine, Delete bot, Delete all messages). The crawl itself unpaired its own phone this way, which then broke the phone run until it was paired again.
- Repro: Settings, This PC, Your phone, click Unpair: the phone stops at once.
- Screenshot: `tests/e2e-2026-11-05/settings-this-pc-phone-card.png`. File: `components/app/setup.tsx` PhoneCard.
- **Fixed: PR #65** (asks in place with Keep).

**M2. A phone whose pairing is gone (or any tab without the window cookie) shows "Loading Bops… This is taking longer than usual." forever.** `/api/state` answers 403 with a reason; the window ignores it.
- Repro: pair a phone, then Pair again or Unpair on the PC; open the phone app (or open http://127.0.0.1:3210 in a plain browser while Bops runs with its token).
- Screenshots: `tests/e2e-2026-11-05/phone-unpaired-stuck-loading.png` (before), `tests/e2e-2026-11-05/phone-unpaired-after-fix.png` (after). Files: `components/app/ui.tsx` useAppState, `components/app/bops-app.tsx` FirstLoad.
- **Fixed: PR #67.** (The Android app's native layer may already catch a rejected pairing, per android/README.md; a browser does not.)

**M3. Chat says "No OpenAI key is set: add OPENAI_API_KEY to .env.local." while Logins shows OPENAI_API_KEY as set.** Self-hosted, the chat reads the key from the environment (`lib/server/openai-client.ts:35`), Logins reads the Orgo vault. A Windows user has no `.env.local` to edit. Screenshot `tests/e2e-2026-11-05/send-no-key.png`. Likely the same split for the This PC "Needs COMPOSIO_API_KEY in .env.local" rows. Needs a decision (which store the chat reads on Windows), so for the lead. If Kevin's Windows app is not self-hosted this does not hit him.

**M4. Memory answers 500 `{"error":"fetch failed"}` when its service can't be reached** (`GET /api/memory?bot=…`, `app/api/memory/route.ts` turns every throw into 500). The bot's Memory tab then says "Memory isn't set up.", which is the wrong reason (it was set up and unreachable). Every bot page and the bot panel log a 500 on open. Suggest 503 with "Memory can't be reached right now" from the route. Small, but the right wording depends on how `memoryFor` reports "not set up" vs "offline", so left for the lead.

### Low

- **L2. Logins on the phone shows "Try again" for a refusal that will never pass** (`/api/keys` 403 for a phone). KeysCard already says "Open Settings in the Bops desktop app"; Logins should say the same. File `components/app/logins.tsx` (the keys fetch).
- **L3. Save stays enabled for a bad cron expression**; the server then refuses with 400 and the page shows `"99" isn't a minute (0 to 59).` The preview line under the field already says what's wrong, below the fold. Screenshot `tests/e2e-2026-11-05/cron-invalid.png`, file `components/app/cadence-picker.tsx` (disable Save while `cronBad`). Good and bad cron strings were all read back correctly otherwise ("*/15 9-17 * * 1-5", "0 9 * * *", "", "99 * * * *", "* * *", "0 25 * * *", "a b c d e", "0 9 31 2 *", 300 x's).
- **L4. Opening Change on a routine whose time isn't one of the suggestions opens with Custom picked and its own chip ("Weekdays at 8 AM") not picked**; clicking Custom then closes the editor and picks the own chip. `cadence-picker.tsx:393`: `custom` starts from `base` (suggestions), not `chips` (which include the routine's own). May be on purpose; flag for whoever owns #52.
- **L5. Save as skill answers 400 when the draft can't be written (provider offline)**, and Compact answers 502; both show Try again in the UI (fine), the 400 is the wrong code (`app/api/skills/route.ts:166`).
- **L6. New bot and group chat names have no length limit in the form**: a 200 character name enables Create; 3000 characters stay in the field (`chat-view.tsx` new bot form). "How Boppy works" (1500) and SOUL.md / MEMORY.md (20,000) do have limits and say "N characters left".
- **L7. Look's Reset and the approval card's Deny act at once** (no confirm). Deny is expected; Reset of the look is mild.
- **L8. Unlabelled icon buttons**: the chat header's bot avatar button and the group chat's "?" button have no aria-label (the crawl saw `button ""`).
- **L9. With the fake Orgo answering 404, the server asked Orgo `/api/user/subscription` and `/api/billing/compute-limits` about 25 times a minute while a window was open** (1,673 and 1,540 calls in the run). With the real Orgo answering 200 this may be cached; worth a look at `lib/server/plan.ts:331` for a failed read not being cached.
- **L10. App logos 404 when logos.composio.dev can't be reached** (`/api/apps/logo/<app>`), one console error per logo, about 200 in the run. The server then shows no logo; harmless but noisy offline.
