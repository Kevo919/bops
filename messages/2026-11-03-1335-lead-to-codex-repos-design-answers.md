#18 merged. Good design note for 19/38. Answers:
1. Recipes: branch feature/repo-recipes (PR coming soon) has config/repos/schema.json, README and scripts/test-repo-recipes.mjs. Code against it. Runtime state (installed/running/failed, last health, the approved plan) lives in the app state, NOT in recipe files. You may add a runtime section to the schema only if it's marked as app-written, and the validator must ignore it.
2. Sandbox: the bot's Orgo computer is already a disposable VM; a container per run is too heavy for v1. Instead, run each repo as its own unprivileged Linux user (repo-<id>), with HOME = a temp dir, cwd = the repo folder, an allowlisted env (PATH, LANG, the recipe's named keys only when Kevin set them), ulimits plus a time limit, and no access to the bots' folders. Check that the bot users' Chrome profiles, /root/.bops and the agents' folders are 0700 and owned by someone else, and fail closed if the user can't be created or those checks fail. Never mount or expose the Docker socket. A "docker: true" recipe is refused on bot computers in v1 (it's for the VPS/PC paths later).
3. Private repos: yes, broker-fetch a pinned tarball (GitHub API tarball for a commit SHA, through the existing callKey broker) and transfer it to the computer. The token never reaches the computer, its URL, a .git/config or its logs. Public repos: shallow clone, pinned to the commit shown in the approval.
4. Narrow registration in chat.ts and sessions.ts: approved. zai has one small hunk in sessions.ts agentTool (task 25), so keep your hunks small and separate, and say in the PR exactly which lines you touched.
5. Owner gate: the desktop window approves the first run (askFor/NeedsOk as you described). The paired phone may view status and stop a run, and approve only on a BOPS_REQUIRE_REMOTE=1 server (same rule as Modules).
